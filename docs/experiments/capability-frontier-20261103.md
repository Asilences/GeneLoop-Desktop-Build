3. 为 C 的关系处理接通受认证的 JSON 值输入：前序能力实际输出由宿主物化为只读 JSON，沿用现有 Script 编译、沙箱及回执。新报告显式认证 65536 字节上限，旧程序保留 16000 字节；不修改 API 输出策略。Linux 定向 17 通过、1 平台跳过，包括跨步骤数据传递与旧输入守卫。
4. 第一轮 C 的 11 次提案包含不符合准入规则的输出写法、代码变量/JSON 错误，以及原生确定性检查失败；全部保留。最后一个关系处理程序通过原生认证并登记材料。它尚不是组合 C，更不是 D。
5. 新材料登记后，旧控制器仍用同一机会的历史失败总数拦截重试，未区分构造时的能力池版本。这是实际接线缺口。现已改为按冻结的构造快照统计，旧事实从不可变结果证据回溯；缺少版本时仍保守处理。随后 C 实际构造成功，失败记录保留。

## 失败已定位到哪一层

- **语义覆盖**：第二条件 Direct 1 与第三条件 Direct 0 将 include 相对当前 Tex 所在目录解析，而冻结协议按归档根目录解析。第三条件实际发布源码 `_resolve_rel` 的 `dirname(base)`、`join(d,t)` 已核对；因此漏掉 `src/ablations.tex`，连带漏变化、missing 和受影响文件。这是生成算法错误，源等价认证没有查出语义遗漏，最终独立检查成功拦截。
- **集合语义**：第三条件 Flat 0 的实际源码 `ekmap` 用 `set().add((path,sha256))`，将完全相同的重复条目去重，漏掉新增重复记录对应的 `changed_entry_keys`。第二个版本对通过也不能使该能力整体合格。
- **准入误拒绝**：第三条件 Flat 1 的 `name.count('/')` 计算目录深度，被误判为未绑定文件路径，连续两次被拒。后续 `f06a0dc` 只给已有分隔符数据运算补 `count`。原程序零模型重放后通过原生认证，但独立训练检查发现 `affected_tex_files` 过度扩散到十余个文件而拒绝发布（期望只有三个）；证据 `code-15/.local/replay-D3-flat1-001/`。误拒绝已修，算法仍不合格，正式六格与费用不改写。
- **选择尚未形成递归**：C 在 Mamba 三个版本的零模型独立深比较均通过（`code-14/.local/C-Mamba-diagnostic/`），但实际 D 没有选它。当前证据排除了这些输入上 C 本身错误及 Runtime 不能嵌套两种解释；尚不能确认模型未选的原因。接口切换成本、普通 Python 无法直接表达已认证能力调用，以及任务本身直接编写已足够容易，都是待分辨假设。

# 上传容量与多轮上下文验收

- 实验 ID：upload-capacity-context-20261103。
- 权威源码：服务器独立分支 `fix/native-upload-context-20261103`，从在用版本建立并合入 GitHub main `944092af`；未用本地旧检出覆盖服务器。
- 问题：任务入口的 768 KiB Base64/JSON 限制会拒绝已经通过图片接收的正常图片；额外场景数量门槛和累计历史输入门槛与原生入口不一致。
- 修改：图片使用原生解码字节额度；普通文件统一 200 MiB；移除场景附件数量和小 JSON 容量门槛；历史附件独立于本轮额度；保留跨场景原始来源、同名版本与各侧产物边界；网页大文件分块上传后由原生服务签发 receipt。
- Motif：Paper v46、PPT v43 是兼容重导出，保留已训练 IR/在线程序、工具 schema、训练/留出和费用证据，0 次训练、0 次重新采样；未修改匹配/学习/认证算法。

- 新图片与多轮回归 5 项通过：9 张超过原门槛的图片、35 份来源后继续上传、同名版本、场景切换、原始图片继承。
- 容量、缓存和错误映射相关 9 项通过；24 MiB 文件字节完整，200 MiB 以上拒绝不影响旧输入。
- 浏览器上传服务和选择器 45 项通过；分块数量、大小、回执形状、失败清理和卸载恢复受检查。
- 完整 Python 初次：2397 通过、10 跳过、10 失败。失败全部集中在 PDF/OCR 测试环境：测试子进程未继承 Poppler 动态库路径、OCR 字库未配置。使用服务器已有工具链的独立测试 wrapper 和字库路径重测；不改动线上工具链。
- 完整 Node 初次：1560 通过、8 跳过、2 失败。其中一项是旧场景文件计数预期；另一项是手动运行 Node 没有设置项目入口原本提供的 `SSS_PURE_CODE_PYTHON`。更新预期并补齐测试环境后重测。
- PPT 文件容量测试原先固定 100 MiB 的哈希和报错预期，现随新公共配置检查 200 MiB 边界。

补充：10 项 Python 失败项在正确工具链环境下全部通过（33.89 秒）；2 项 Node 失败项更新预期/补齐原入口环境后全部通过；PPT 文件容量 4 项全部通过。原生 20 MiB 图片存储检查通过。

验收使用服务器已有 DeepSeek Flash / off，沿用累计账本和应用不限预算配置、官方原生输出容量；通过新注册测试成员验证多用户并行、历史图片、跨场景多轮、较大有效 PPT、问候不重复解析说明，以及公网超过单次 HTTP 容量的大文件分块传输。

原始日志、账号凭据、完整模型输出留在服务器私有目录；本记录不包含用户数据或凭证。无模型检查不是模型质量结论。最终结果见下方发布验收记录。


### 真实验收发现的第二层数量门槛
第一轮真实任务中，2 位成员并发、图片识别、Chat→Data→问候→10 份 Paper 附件→追加 Data 附件均通过；32,575,159 字节的有效 PPTX 上传及 Baseline 读取成功，Motif 准备失败。私有诊断为 `rsi_requires_approved_sources`：来源绑定适配器仍保留 8/16 份计数门槛，累计历史后再次触发。已移除该重复计数条件，保留非空来源、路径、权限、哈希及工具契约校验；新增四类绑定器的 36 份来源与末份文件篡改拒绝测试。Paper v47 / PPT v44 继续只做兼容重导出。

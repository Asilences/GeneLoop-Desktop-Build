## 结论与归因边界

已证实重复图片和过宽的 Bash 保护增加了优化组的冗余工作；已修复源代码。**它们不能完整解释上游缓存命中率的差异。** 原请求没有保存实际出站消息指纹，不能倒推出上游缓存键、路由或图像计量方式，也不能声称本次免费诊断已经证明费用下降。

已完成配对的真实计量保持原样：B 79 请求、O 52 请求；成功且有可用 usage 的输入分别为3,459,680与1,715,610，缓存命中3,061,504与790,258，未缓存输入398,176与925,352。命中率88.49%与46.06%；O少请求却多527,176个未缓存输入。输出28,012与28,038几乎相同。在当前未核实的配置费率下，未缓存输入是缓存输入的50倍，因此已报部分估费B USD0.171436224、O USD0.315992748。HTTP502未知收费和Kouri实付均继续标为未知，不改写为零。

SDK 的 `inputTokens` 是未缓存部分，须加 `cacheReadTokens` 才能与网关总输入核对。本次逐项核对成功响应与 assistant 事件，保留已修复的标准缓存字段解析，没有证据表明本次差异由解析器丢失缓存字段造成。

## 已定位的问题

1. **缓存异常先于图片。** O首次返回图片前13次成功模型请求已有197,501个未缓存输入；多个请求命中为0或仅1024。认证目录在初始system中出现一次，未发现再次作为user通知注入。不能把整段缓存损失归咎于重复目录或看图。
2. **上游usage存在明显异常信号。** 请求18635/18636/18637的输入上界分别449,810/450,526/451,155，来自发送体字节和图片数量的保守计算；对应实际已报总输入31,392/255,196/34,600。中间请求零命中、输入突增约八倍，而发送体上界几乎不变；本地回执文字只有66字符。没有原始出站body，不能确认是上游路由、图像处理还是usage回报差异，更不能擅自重算账单。
3. **连续程序忽略已有图像。** 学得程序的预览集合绑定到所有PNG，修订第二页也再次读取第一页。O生成9次图片返回只有6个不同hash，其中3次重复，共577,281字节的规范化附件元数据体积；改页又返回一次完全未变的第一页。此数不是实际HTTP图片体积或省下的token。
4. **同图重复读取。** 连续程序已返回第二页Office PNG，模型下一次仍单独read_image同hash。旧工具说明只要求“返回后read_image”，没有区分自动续接已返回的图。
5. **保护过宽。** 有受管页面就拒绝所有Bash，既拒绝覆盖页面，也拒绝`cd .../svg_output && sha256sum *.svg`和混合的最终整理/检查。原始最终命令含变量、cp及任意Python，不能仅删除整个保护。实际记录保留在原配对轨迹。
6. **共同冗余。** 两组均在原生Skill后读取MCP skill entry；O还在组件临时PNG之后重复查看SVG、字体属性和原文摘取。重复读取并非全部错误：具体事实或图件核验仍应读原文。取消无依据的重复流程，保留必要科学校验。

补充交叉核对：两侧完整会话各只有一次request/header和一次system/message，surface操作只有append，未记录context replace。成功agent响应中，B有62/63次的`total-input-output=59`，O只有2/37次，其余为0。同一出站模型配置的两组出现不同的上游usage格式足迹，**提示需要核对上游路由/计量一致性，但不能据此认定实际换了模型**。缺少实际出站body和上游响应身份，保留未分类token，不擅自消去差值或调整费率。

原任务顺序为O先B后，存在共享上游缓存预热的混杂，且B本身有更多修稿/裁图。不能从这一对数据证明“RSI导致所有缓存损失”。不补跑来寻找更好的数字。

## 本次源代码修复

- `ppt_delivery_pipeline.ts`：使用当前LLM请求、SDK公开图像投影接口、附件请求版本的实际字节及当前连接的文件/内联限制，保守计算两种传输都保留的图片。未知配置、text-only、已卸载或压缩掉的图片均正常返回，不伪造已看图。仅把后续相同附件替换成稳定引用；首次图片、历史消息、规范工具value和全部原产物均保留。引用明确不代表质量通过。配置通过`dsh_web_tasks.ts`的现有宿主接入，未改上游核心。
- 同会话私有workspace保存原始PNG hash与规范化附件ID之间的绑定，后续任务可关联同字节图片。连续程序只有在当前模型请求确实保留该图时才跳过再次读取；变化页仍读，首次仍检查全部页面。不同workspace不共享。
- `ppt_write_runtime.ts` / `ppt_write_tool.ts`：宿主决定预览复用范围，解释器不自行创造学习流程。返回已复用hash，受管页面写入、版本、取消、来源与其他页不变检查保留。已有学习程序须按新执行环境重新认证，不手改证书或pointer。
- Bash准入仅放行小范围字面量只读校验和`/work/outputs`内的mkdir/cp/ls整理；仍由原生工具执行。变量、代码执行、重定向、管道、父目录跳转及项目写入不在放行范围。复杂混合命令仍拒绝并指向现有read/present；直接present回执产物无需先复制、改名或重复检查对象。
- 统一Skill、场景prompt、工具说明：初稿完成后看Office输出；已返回图不重读；来源索引用于定位、具体事实仍核验；原生Skill已加载不重复加载同一entry。同一完整说明确实已在模型请求中加载时，MCP读取的模型可见说明改为hash引用，完整canonical value、版本、策略和来源目录保留；说明有变化或其他中间件已有定制内容则不压缩。未改变用户题面，不截断上下文。
- `request_fingerprint.py` / `deepseek_cost_gate.py`：对实际出站请求记录body/envelope及有序消息hash、字节数、图片数量、重复图片payload数和与同一会话前次的共同消息前缀。只记录hash和数量，不保存正文、路径、URL、像素、认证头或密钥。记录不改变请求，不等于上游缓存命中证明。原预留、未知费用和账本规则保留。

本次是执行层工程修复，**不称为新学得的Motif**，也不把减少图片返回量等同于减少真实模型请求或费用。

另查到测试预算broker只转发Chat/搜索/视觉，Files API请求被本地404拒绝，SDK因而会使用内联图片；不能假设已有file_id复用。此次保留原路由，覆盖内联退化的复用检查，不在未确认Kouri Files API支持和权限隔离前扩建该接口。此共同限制不能单独解释两组命中率差异。

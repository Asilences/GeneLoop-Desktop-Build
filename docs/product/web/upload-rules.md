# GeneLoop 上传与附件上下文规则

更新时间：2026-11-03。容量采用二进制 MiB（1 MiB = 1,048,576 字节）。

| 输入 | 当前规则 |
| --- | --- |
| 图片 | 复用 DSH 原生 imageLimits：默认单张 20 MiB，每条消息最多 20 张，原始图片合计最多 200 MiB；按解码后的图片字节计算，不按 Base64 字符数计算。 |
| 图片像素 | 保留 DSH 的图片格式、解码、尺寸检查：默认最长边 8192 像素、最多 6400 万像素。 |
| PPT/PPTX、PDF、文档、数据、视频等普通附件 | 单文件 200 MiB。图片文件进入图像通道时仍遵循图片规则，不能用文件入口绕过。 |
| 场景数量限制 | 移除 Paper 16、其他场景 8、File 40 等额外附件数量门槛。场景不另设小于原生图片规则的入口额度。 |
| 大文件网页传输 | 超过 16 MiB 的普通文件分为最多 8 MiB 的块上传；最终由本会话的 DSH 原生上传服务生成 receipt。中断会清理临时数据，过期临时数据也会清理。 |
| 压缩文档解包 | 保留路径穿越、链接、条目数和解压后容量保护；相关文档解析器解压总容量提升为 1 GiB。接收一个文件不保证损坏或异常压缩文档可解析。 |

普通文件容量由 `src/adapters/geneloop_upload_limits.json` 集中配置，TypeScript 和 Python 入口共用，避免前端、任务适配器和解析器容量不一致。图片容量直接取原生附件服务配置。

## 多轮与场景切换

- 本轮内容只包含本轮新提交的文字、图片和文件。历史附件通过历史来源引用保留，不伪装为“本轮重新上传”，不计入本轮图片配额。
- 同一对话切换 `/paper`、`/ppt`、`/data` 或返回 Chat，仍能引用此前附件；不按新场景后缀过滤掉历史来源，也不因累计附件数量超过旧门槛而丢失资料。
- 同名文件保留独立来源与版本；新版本不会静默覆盖旧版本。
- Baseline 与 Motif 共享用户明确提交的原始资料，各侧历史产物保持分离。不同用户、不同父对话的附件不能相互继承；receipt 所属会话、哈希与权限校验保持启用。
- 大附件按文件逐个暂存和校验，全部通过准入后才绑定输入，避免同时把整批大文件常驻内存；失败不会先清掉原输入。

## 协议边界

这里规定的是应用接收和原生图片准入容量，不是模型上下文无限，也不取消网络协议、图像解码、压缩包或输出交付的保护。普通大文件使用分块传输；图片消息仍经过原生消息传输与模型图像预处理。模型可通过文件工具按需读取大文件，不能据上传成功宣称全部内容已被理解。

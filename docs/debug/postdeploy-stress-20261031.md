## 修复内容与原因
用量统计的只读查询发生短暂网络断开或超时时，旧适配器将异常传到对照协调器，导致界面将整轮任务标成失败，而原生任务仍在后台运行。
现在仅容忍这类统计传输异常，保留任务实际状态及已知用量，标记用量待同步；后续成功查询恢复完整计量。没有重发模型请求，也没有放行权限错误或 HTTP 拒绝。HTTP JSON null 错误体也能正确处理。
Paper / PPT 认证包绑定适配器源码哈希，所以重新导出 Paper32 / PPT29 兼容版本。原程序、schema、证据逐项一致，保留旧包；没有重新训练、修改匹配/认证算法或撤销守卫。

- Paper：10 个分支均交付 Markdown / PDF，并指出题目中预设的算术错误。
- PPT：10 个分支均交付可编辑的 3 页 PPTX 与 3 页 PDF；本轮没有进行人工设计质量盲评。

- 公网实际入口：5 个账号各 2 轮，共 10/10 通过，能够正确回忆本账号当前对话的标记。登录页与 Logo 返回 200，哈希与当前服务一致。

## 必须保留的失败与人工介入
1. U1 的 Data 初始轮返回了正确字段与数值，但 JSON 前后附带解释文字，严格格式检查失败；这是尚存的模型遵循性问题，没有改成通过。
2. U5 的 PPT 问候曾因“重建页面视觉”被检测器的单独“视觉”关键词误判为附件重放。服务器上修正检测器，仅识别具体的旧附件/视觉覆盖声明，并添加正反例测试。原始结果保留，最终审计另存。
3. U2 的 PPT Baseline 等待 ask_user_question 选择是否做风格归一化，超过测试客户端 30 分钟等待窗口。依据用户此前自主设计授权，选择“不归一化，直接交付（推荐）”，原任务随后完成并通过文件检查。没有另起模型任务，也没有由验收者制作或修改 PPT；此项包含一次人工确认，不算无人值守通过。
4. 公网统一 public-check 的 10 秒诊断探测经反向 SSH 中继未通过，两个失败收据保留；直接公网 10 轮业务测试通过。不能将这解释为所有网络路径都稳定，也没有完全证明早期公网 POST 断连的根因。

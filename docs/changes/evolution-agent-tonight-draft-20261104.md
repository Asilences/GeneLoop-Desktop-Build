# Evolution Agent 今晚实现草案

日期为 2026-11-04。状态为待实施草案，分层上下文属于首版参考设计，具体呈现方式根据真实调查过程调整。

2026-11-05 更新。用户指定八小时内优先完成核心机制及可运行实验，费用与请求次数不限。主对照选用 Skill∞，优先使用其 SkillsBench 数据与评分流程，慢任务和 KernelBench 根据实际耗时后置。实施窗口从恢复开发时记录实际起点。

## 1. 今晚只抓住一条主线

让 Evolution Agent 自主查阅真实经历和当前能力，提出具体改进，经原流程构造与评价后进入后继行为，再根据实际结果继续调查和修订。

核心问题是，已学到的抽象能否改变后续求解与能力创造的起点。

```text
当前能力库 M + 执行/构造经历 G + 实际反馈 F
                     ↓ 按需查询
             Evolution Agent 自主调查
                     ↓
          改进假设及预期的后继行为变化
                     ↓
            原构造、编译与独立评价
                     ↓
          更新的能力或构造策略进入后继行为
                     ↓
           新的 G、F 回到下一轮调查
```

原 Motif 学习器继续从真实轨迹提取稳定结构。Evolution Agent 结合实际反馈，决定哪些抽象边界、表示或构造方式值得改变。两条路径共享原能力库与构造流程。

## 2. Evolution Agent 的职责

每轮自主决定以下事项。

1. 查哪些经历和能力，是否需要比较其他做法或反例。
2. 问题可能来自哪里，是否值得提出改进。
3. 具体改变什么，预计怎样影响后继行为。
4. 读取实施与评价结果后，继续修订、保留候选或结束本轮。

首版使用固定 Prompt 和现有 Harness 的工具调用循环。模型提出问题判断与改进假设，原 Builder、learner、Runtime 和评价流程承担实现与执行。

候选可以是新能力、现有能力的边界或表示变化，也可以是构造策略变化。具体后继目标由真实调查形成，允许 `no_change`。

首个纵切优先覆盖能力构造经历及后继 Builder，任务执行经历使用相同查询设计。该优先级属于本草案建议。

## 3. 分层上下文参考设计

### 第一层，启动概览

每轮开始提供以下简短内容。

- 当前研究目标及允许调查的数据范围。
- 能力库规模、已有分类与近期变更。
- 新增任务和构造的数量、结果状态及已知费用概况。
- 上轮改进及目前观察到的后继表现。
- 可用查询、构造和评价工具的说明。

这一层帮助 Agent 选择调查方向。完整能力目录与轨迹通过工具访问。

首版可尝试约 1–2k Token 的启动概览。这是信息呈现的参考尺寸，运行时记录实际输入长度。原记录完整保留。

### 第二层，检索与比较卡片

Agent 主动查询相关能力或经历，工具分页返回简短卡片。

| 对象 | 卡片内容 |
| --- | --- |
| 能力 | 功能、输入输出概述、版本、依赖概况与已有使用信息 |
| 经历 | 原决定身份、已有目标描述、实际能力调用、结果、修复次数、已知费用及局部证据入口 |
| 历史改进 | 改动对象、假设、采用情况、已有评价与反例入口 |

目标描述优先复用已有材料，缺失时保留来源入口。收集与索引阶段由代码读取已有事实，语义解释在调查中按需生成。

查询可按能力、阶段、结果、费用或已有文本检索，并支持查看不同做法及反例。返回数量、分页位置和省略范围可见。

### 第三层，局部事实与跨任务比较

Agent 选定对象后，读取相关局部过程。

- 任务侧可查看某次能力调用前后的状态、输入输出、后续决策与结果。
- 构造侧可查看材料选择、能力组合、编译、验证和修复过程。
- 支持同时取出几个独立经历中的相关片段进行比较。

工具负责定位和投影原始事实，Agent 判断共同问题及可能原因。实际独立任务、同一任务重试和续写保留来源关系。

### 第四层，原始材料核对

Agent 对具体疑点继续读取请求输入输出、Motif 内部图、实现、验证详情或费用明细。读取支持对象定位、范围选择与分页。

四层提供不同读取粒度，Agent 可以跳层、换方向或结束调查。

### 调查工作便笺

Agent 在阶段性节点维护简短便笺，保存当前假设、支持与反对证据引用、已排除的解释及下一步问题。

上下文压力通过现有 Harness 检查点与压缩机制处理。便笺作为可回溯的调查状态，原始材料仍可重新读取。下一轮启动只携带相关结论与引用。

## 4. 首版工具能力

下列名称表示建议接口职责，实施时复用现有公开工具接口和证据读取逻辑。

| 能力 | 返回或产生的内容 |
| --- | --- |
| 获取概览 | 第一层概况及查询入口 |
| 检索能力、经历和历史改进 | 第二层分页卡片 |
| 读取局部证据或原始材料 | 第三、四层可定位内容 |
| 提交改进并调用原构造流程 | 候选规格、构造产物与执行记录 |
| 调用原独立评价并读取结果 | 质量、行为差异、完整成本与失败 |

同一 Agent 会话可以根据工具结果继续查询、修订或结束。代码实现时先确认已有单次提案入口到原 Harness 工具循环的接缝，沿用原模型调用与费用账本。

## 5. 候选最少需要表达什么

候选把三件事连起来即可。

1. 哪些实际证据支持这个问题判断。
2. 具体改变哪项能力、表示、边界或构造方法。
3. 后继任务或 Builder 预计会换成什么做法，以及怎样观察该变化。

候选进入原实现与独立评价流程。评价结果与实际后继采用情况返回 Agent，供继续修订。质量要求沿原检查器执行，费用覆盖调查、提案、构造、验证、失败和修复，并分别报告一次性投入与后继运行成本。

## 6. 异步产物交接与 Prompt 式策略匹配

Evolution Agent 与执行 Agent 独立运行。Evolution 根据已经积累的经历完成一轮调查、构造和评价，并发布成果。后继任务或 Builder 从已发布成果中按需选择，执行结果再异步回到 Evolution。

```text
Evolution 批次调查 → 构造与评价 → 发布能力、策略或适配改进
                                      ↓
                       后继任务／Builder读取成果快照
                                      ↓
                         匹配、采用并产生真实经历
                                      ↓
                         后续Evolution批次再调查
```

### 成果按实际载体进入后继过程

| 成果 | 生效入口 |
| --- | --- |
| 可执行抽象 | 原能力目录与Runtime，沿已有结构匹配、语义检索和调用流程使用 |
| Prompt式决策策略 | 当前执行或构造Agent的策略目录，按问题需要读取并采用 |
| 表示或接口改进 | 能力新版本的接口，或GeneLoop自有Harness插件、上下文装配与适配代码 |

接口与表示变化若涉及代码，由原实现流程形成可审阅补丁，经测试与评价后更新对应适配版本。策略发布使用原sidecar、版本引用和配置交接。适配代码发布通过原代码与服务流程完成。仓库既定路线是使用上游Harness的公开插件及MCP接缝，GeneLoop侧负责自身适配。

### 首版采用简单的Prompt式匹配

策略保留简短目录项和按需读取的正文。目录项说明名称、适用问题和作用位置，正文描述条件与方法，并引用相关能力。原策略sidecar保存对应信息。

下一次任务或Builder启动时读取已发布成果快照，将与当前范围相关的少量策略目录项放入上下文。可先按任务／构造范围筛选，条目增长后使用已有文本检索缩小候选。原Agent依据当前问题判断是否相关，通过查询入口读取所需正文，再决定采用、调整或忽略。

默认Prompt可采用以下含义。

> 你可以查询已学习的策略。根据当前任务、已有能力和进展判断是否有相关方法，按需读取其内容并决定如何使用。发现条件不符时继续选择其他方法。

策略可描述适用于规划、能力组合或修复的情形。Agent在原有决策过程中查询这些方法，实际采用由当前问题决定。首版沿用原Agent的模型决策与工具循环。

### 及时使用与反馈

评价通过的成果登记到研究范围内的可用集合。下一次任务或Builder调用获取新快照，已开始的执行段继续使用其既有版本。记录当次可见策略、实际读取的正文版本及后继调用和构造结果。

下一轮Evolution据此区分可见、读取、声明采用和实际行为变化。读取策略正文说明获得了相关信息，是否产生帮助仍由后继质量与完整成本判断。

首个匹配验收需要包含相关与不相关问题，观察原Agent是否能按需读取、合理拒用，并在采用时产生预期的行为变化。保留漏检、误用和无收益结果。

## 7. 实施顺序与依赖

### A 先打通自主调查

- 将已有能力、任务和构造记录接到上述查询入口。
- 为原 Evolution 入口接入现有工具调用循环。
- 提供固定 Prompt、启动概览和调查便笺。

验收时查看真实模型如何选择对象、查询证据、形成判断或结束调查。记录每次工具调用、上下文长度与实际费用。

### B 再打通改进与后继采用

- 将 Agent 候选路由到原能力构造、边界演化或策略流程。
- 调用原独立评价，返回实际结果。
- 将通过评价的成果异步交接给研究范围内的后继 Builder 或任务。
- 完成第6节的策略目录、正文按需读取和Prompt式匹配，能力及适配类成果进入各自生效入口。

验收时从候选追踪到实际后继行为，保留具体调用或构造差异。

### C 最后打通结果回流

- 将后继行为、质量与完整成本加入可查询经历。
- 下一轮 Agent 能查询上一轮改动及结果，自主保留、修订或放弃。
- 已产生受支持稳定执行片段时，交给原 Motif 学习器继续发现与认证。

验收时观察第二轮的真实调查和选择如何利用第一轮结果。

```text
A1 记录与能力查询 ─┐
                   ├→ A3 真实自主调查
A2 工具循环接入 ──┘          ↓
                      B 改进与后继采用
                              ↓
                      C 反馈驱动下一轮
```

A1、A2 可在接口确定后并行。每阶段先做针对性诊断，再做真实模型验收，最后运行受影响的原有回归。

## 8. 今晚的交付与判断依据

主交付是一条可检查的真实运行链，能够回答以下问题。

- Agent 启动时实际看到了什么。
- 它自主查了什么，调查费用和上下文开销是多少。
- 它基于哪些证据提出了什么具体改进。
- 原流程是否完成实现与独立评价。
- 后继运行看到了哪些异步发布的成果，实际读取并采用了什么。
- 后继 Builder 或任务实际改变了什么。
- 下一轮如何使用新结果继续决策。

查询、提案、构造、后继采用和收益分别报告。若结果为失败、无可用候选或 `no_change`，保留完整调查路径，据此定位下一步问题。

先复用现有论文与构造材料，在受支持范围内完成接线诊断，并接入第10节选定的benchmark小批任务。两类结果分别记录。真实模型实验在已配置服务器运行，记录实际模型、模式、预算和输出配置，费用沿原累计账本。

## 10. Benchmark与baseline

### 已核实的来源

Skill∞在SkillsBench上使用SkillEvolver发布的训练数据与83个测试任务，另测三个KernelBench level-3问题。其主要实验采用Codex CLI、GPT-6 Luna和Harbor，SkillsBench结果使用每题五次试验的avg@5。论文包含seed meta-skill，可用于研究复现。实际任务清单与完整复现差异需进一步逐项核对。[Skill∞论文](https://arxiv.org/html/2610.35434v1#S4.SS1)

截至2026-11-05查询，Skill∞官方仓库仍标注代码即将发布。主baseline确定为Skill∞，实现来源待用户确认论文复现路线。直接使用seed进行任务优化的配置需要单列为seed版本，完整baseline还应包括meta-skill自我改进及其成本。[官方仓库](https://github.com/taowangcheng/skill-infinity)

SkillEvolver公开了训练变体、测试数据准备方式和SkillsBench固定版本。优先核对其数据交集及原评分器，锁定实际使用的commit、任务与文件哈希。当前SkillsBench主线已有版本演进，精确任务对齐以论文所用发布链为依据。[数据准备脚本](https://github.com/THU-AICosmos/skillevolver/blob/main/scripts/setup.sh) [训练与测试说明](https://github.com/THU-AICosmos/skillevolver/blob/main/docs/skillsbench.md)

### 今晚优先测什么

首批从上述数据交集中选择预计较快、无需额外外部服务、原评分器可运行的CPU任务，目标先覆盖约4–6题、至少两个领域。任务清单在正式比较前固定，数量依运行时实测调整。

先核对容器、评分器和静态依赖，再用小规模运行估计耗时。时间允许时扩到更多任务和五次独立试验。单次结果标为单次，试验数随结果一起展示。

选择与暂缓依据包括环境可运行性、依赖准备时间和事先定义的超时规则。已进入比较的任务保留两侧结果及超时状态。额外耗时或依赖不具备的任务列入明确的暂缓清单。

KernelBench保持第二优先级。首轮只在GPU、正确性检查与真实计时路径均可运行且核心纵切完成后启动，记录具体问题、硬件与环境。[KernelBench原论文设置](https://arxiv.org/html/2610.35434v1#S4.SS1)

### 对照怎么做

主比较为GeneLoop与Skill∞。双方使用相同基础模型、推理档位、任务、输入版本、容器工具和原评分器。首选已配置的DeepSeek真实API，实际型号从服务器有效配置记录。该路线得到的是同模型适配比较，原论文成绩单列为文献参考。

Skill∞复现需保留其meta-skill自我改进、任务skill优化、独立review及名称／描述驱动的原生发现，并明确所有复现差异。使用原生skill发现的适配入口应先验证，具体Harness版本共同冻结。

GeneLoop组启用本草案的查询、演化和继承机制，记录策略与能力实际采用。保留同一GeneLoop起始快照用于演化前后比较，帮助区分基础执行能力与本轮演化贡献。

### 两层数据划分

- 方法层将用于改进Evolution策略／meta-skill的任务，与评价其跨任务作用的任务区分开。
- 任务层沿原数据发布的训练变体与canonical测试任务划分。两侧获得相同范围的可用材料，测试评分在冻结版本后执行。

训练变体和canonical任务保留共同的任务身份。同题多次尝试作为重复试验记录。连续任务流中记录每次测试前可见的能力、策略和经历快照，便于核对跨任务继承来源。

### 同时看方法闭环和实际效果

| 问题 | 报告内容 |
| --- | --- |
| 是否完成任务 | 原评分结果、每题试验数与通过率 |
| 是否提高效率 | 同质量条件下的完整费用、首成功成本、耗时与修复 |
| 是否采用了演化成果 | 查询、策略读取、能力调用和构造变化 |
| 是否发生递归积累 | 已有能力参与后继真实图或构造，原learner继续消费并形成后继能力 |
| 反馈是否改变方法 | 下一轮抽象边界、表示或构造方式的具体变化与结果 |

双方完整计入方法自我改进、调查、生成、验证、独立review、失败和最终测试开销，一次性投入与后继运行分别列出。实验费用不限，比较时展示实际质量—成本关系及算法搜索配置。论文中的候选数量作为复现参数核对，实验运行沿原累计账本连续记账。

## 11. 八小时时间分配

以下为推进优先级和检查节点，实际耗时逐段记录。

| 时间段 | 核心机制线 | Benchmark／baseline线 | 检查点 |
| --- | --- | --- | --- |
| 0–1小时 | 核对基线和暂停草稿，固定工具接缝 | 锁定数据版本、模型和首批任务，核对评分器；确认baseline来源 | 能启动首个原任务与真实调查 |
| 1–3小时 | 接通分层查询和原Harness工具循环 | 建立共享任务执行与评分适配，接Skill∞复现入口 | 调查记录和单任务两侧执行可重建 |
| 3–5小时 | 接通候选构造、异步继承及后继反馈 | 运行首批训练与评价，保留失败和耗时 | 候选实际进入后继行为 |
| 5–7小时 | 观察下一轮反馈修订，检查原learner输入 | 扩展已准备任务和重复试验，核对完整费用 | 形成最小可比较结果及机制证据 |
| 7–8小时 | 集成审计与受影响回归 | 汇总两侧结果、失败、费用和暂缓任务 | 提交可审阅代码、复现入口与报告 |

环境与机制性阻断优先定位。任务扩展随可用时间调整。回归、独立评价及失败保留优先于扩大测试数量。费用与请求上限使用原协议中的不限值，CLI表示方式以实际入口为准，原累计账本保留。

## 1. 这轮到底准备做什么

建议首批实现三个相连的部分：

1. **把一次能力构造的全部尝试、成本和失败位置连起来**，知道钱花在哪里、卡在哪里。
2. **让原 Builder 在必要时重新选择实现做法**，同时看到已有能力、已经失败的做法和实际成本，而不是只继续修上一份程序。
3. **用一次受控真实验收检查这条反馈是否实际生效**，保留没有换策略、没有使用高层能力、成本反而上升的结果。

本轮交付的目标是：新能力和构造经历能够进入下一次构造决策，决策及其后果可核对。是否产生 Creation Efficiency 增益，另由真实结果判断。

暂不实现预算再投资账户、自动学习的策略评分、长期 Creation Value 估计、用户间能力共享或生产接管。

## 2. 为什么现在做这三项

我们的目标仍然是效率驱动的 RSI：已有抽象降低后续能力获取所需的投入，使有限预算能够支持进一步创造。

这里需要区分两种效率：

- **执行效率**：同一质量门槛下，完成当前任务需要多少投入。
- **创造效率**：同一质量门槛和总预算下，获得下一项可复用能力需要多少投入，或者原本预算内没能获得的能力是否变得可达。

调用 C、生成 D 或增加库的规模，都不能单独说明创造效率提高。构造成本要包含发现、模型生成、缺口学习、修复和独立验证；未知部分仍然未知。有限预算内能力可达性的结论继续遵守现有计量协议，不把一次失败当作普遍不可能。

你提出的关键判断是“局部 action 压缩，上层 strategy 扩大”。对应到工程上，需要让模型有机会重新决定**如何解决问题**，并让过去的执行事实影响这个决定。

例如，原做法是每次完整重写跨版本审计程序。已有单版本审计能力 C 后，模型可以考虑用 C 分别审计，再只实现差异关系；也可以选择直接编程、混合实现或暂缓。宿主不预先规定必须使用 C。最终依据执行和质量结果判断这些做法的代价。

此前路线把“预算再投资”列为下一 PR。本计划建议先补构造事实与策略选择的连接，再接再投资。预算接口继续保留；这次顺序调整的原因是最新讨论要求先弄清楚 Creation Efficiency 如何影响下一次自我改进。

## 3. 已有代码能做什么，具体缺什么

| 已有部件 | 当前行为 | 本轮需要补的连接 |
| --- | --- | --- |
| `capability_opportunities.py` | 新能力发布后，基于未满足需求提出目标，宿主筛选后入原队列 | 新目标之后，实际如何选择做法及其成本后果需要连起来 |
| `capability_improvement.py` | 原构造、修复、缺口学习、认证、发布与暂缓重试 | 在明确的节点允许重新考虑做法，并记录相应来源 |
| `capability_proposal.py` | 提供冻结任务、能力目录、上次回答和修复反馈 | 缺少面向同一目标的历次构造结果与成本视图；当前修复信息主要围绕上一轮 |
| `capability_feedback.py` | 成功构造贡献参与排序；同范围执行费用参与执行选择 | 成功次数不是创造效率，不能据此给能力宣称因果收益 |
| `efficiency_rsi_registry.py`、`efficiency_rsi_measurement.py` | 请求归属、全程支出与首成功成本分开计量，保留未知和失败 | 将构造决策与这些原始计量引用关联，供下一轮读取与事后比较 |

以上机制复用，不另写 Harness、Runtime、费用总账或第二套 Agent 循环。

## 4. 第一项：构造记录和失败定位

**实现什么。** 对同一目标提供一份可重建的构造过程视图：需求、任务契约、能力池版本、每次提案、缺口学习、修复、验证、发布，以及各环节原始请求和费用引用。

**为什么。** 看到“复用 C 更贵”后，要能直接分辨：是接口绑定反复失败、新算法本身难、验证开销高，还是模型一直沿用不合适的做法。不能仅靠最后一次成功回答猜测原因。

**怎么实现。** 从现有 journal、attempt 目录、PR #126 目标账本、请求 registry 和验证回执生成视图。优先补来源关联与读取函数，不复制一套可独立修改的费用事实。

- 宿主填充任务 ID、版本、请求归属、时间、实际费用、检查结果和回执；不让模型重复生成这些字段。
- 错误位置来自现有编译器、学习器及验证器的诊断。无法从证据定位的原因标为 `unknown`，模型解释另存为假设。
- 全部尝试费用与首个合格能力的获取成本分开呈现；发现和验证等共享费用明确归属，不能丢到表外或重复计算。
- 预期、编译和实际执行依赖沿 PR #126 的记录分开；成功发布、实际调用和相对收益分别判断。

**验收。** 给定保存的历史尝试，可不调用模型重建费用与失败链；未知用量不按零算，失败不丢失，同一请求不重复计费；读视图不改旧实验或账本。

## 5. 第二项：在原构造流程中重新选择做法

**实现什么。** 为原 Builder 增加一个默认关闭的研究选项。在新能力进入可用池、或现有规则已经判定当前修复应暂缓时，允许一次受预算约束的重新选择。它可以保留做法、换做法、请求缺失材料或暂缓。

“换做法”的实际含义是：下一份构造可以改变依赖组织、采用不同分解、写新叶程序或直接实现，不局限于修正上一份提案的字段。模型原有编程能力保留。

**为什么。** 精确错误反馈有助于修好当前方案，但仅补参数或包装并不能保证模型会重新考虑整个方案。我们需要把重新选择的机会和输入做实。

**怎么实现。** 扩展原 `prepare_attempt` / `propose_once` 与宿主适配器的构造上下文，仍通过原控制器调用、编译和验证：

1. 输入冻结的原目标、质量契约、当前能力池、新增材料、第一项生成的历史事实及剩余授权预算。
2. 在同一次构造回答中允许模型给出简短的做法说明、预期使用的能力及选择理由，再给现有受支持的程序或组合提案。具体编码在实施时按现有版本协议整合，旧回答路径保留兼容。
3. 宿主记录“本次为何重新选择、模型声明的做法、实际编译和执行结果”。宿主不替模型指定算法，也不依据自述认定策略已经进化。
4. 新材料的版本变化后重新冻结输入。现有修复要停止时，重新选择的额度必须显式配置；它不重置原重试计数、累计支出或预算，不反复唤醒相同失败。
5. 权限、证据、版本或基础设施错误继续按原规则拒绝或暂缓，不借重新选择绕过守卫。独立质量条件始终不变。

不增加单独的“规划 Agent”或默认额外的反思请求。初版以原构造调用消费上下文；暂缓后的额外尝试须属于明确授权的有限研究配置。

**验收。** 能记录保持做法、改变做法与暂缓；同一事件不重复触发；缺预算不调用；质量与权限不变。通过最小离线夹具验证上下文与结果的关联，随后用真实模型检查是否读取并响应这些信息。文字标签或程序哈希变化不作为策略改变的充分证据。

## 6. 第三项：真实验收，先回答两个小问题

第一轮只检查：

1. 新能力和构造历史是否真的进入下一次模型决策，而不是只存进文件？
2. 模型能否在原做法受阻时选择另一种可执行做法，并通过原独立检查？

先选一个现有真实工作流中尚未满足的需求，保留正常 Agent 的编程和工具能力。冻结任务、初始能力池、模型、质量标准和有限研究费用上限；既有材料、原件和账本不修改。算法与必须调用的前代能力不预置。

初步对照为：A 使用当前构造及修复信息；B 在相同基础条件下额外消费构造历史、实际成本及重新选择上下文。两组使用相同的总研究预算和质量门槛，保留所有失败。新机制自身的额外调用和开销全部计入。

这项对照只能先回答反馈上下文是否有用。单独判断 C 本身的创造价值，还需要能力可用性与反馈条件分开的对照；不能用 A/B 的差额直接归因于 C。

交付包括：模型实际看到了什么、选择了什么、构造和验证是否成功、实际依赖、全部费用、失败位置及人工介入。首次模型配置与有限预算另在实验开始前固化；写本计划不启动付费调用。

如果效果不理想，直接按证据和用户一起定位：未看见能力、看见但未采用、接口困难、新算法缺口、质量失败，或模型已选了更合适的简单做法。定位不出的部分保留未知。不为获得正结果持续改某个场景或筛选成功谱系。

## 7. 开发顺序与停止条件

| 顺序 | 交付 | 完成条件 |
| --- | --- | --- |
| 1 | 构造过程视图与原记录关联 | 历史失败可重放，费用守恒、未知保留，不修改旧证据 |
| 2 | 原 Builder 的上下文与重新选择接线 | 默认路径不变；触发、停止、版本和预算约束通过正反回归 |
| 3 | 隔离真实验收及简短定位报告 | 原始请求、实际行为、独立质量和全程费用可核对，失败同样交付 |

本轮代码范围以公共 Python 离线构造模块、现有 schema/适配器及必要测试为主；不引入新的在线 Runtime。公共接口变化同步到 `docs/interfaces.md`；实施及真实验收状态更新到主线交接。

公共机制变更后执行仓库要求的 `npm test` 及相关 smoke；确定性测试只证明流程与守卫。Linux 隔离环境中的真实模型验收才用于判断模型行为。

流程验收通过但没有观察到收益时，机制状态与效果状态分别记录。是否扩大实验由后续真实证据与用户判断；不把小样本增益设为继续工程的硬门槛。

## 8. 后续路线保留什么

当本轮事实能够支持判断下一次构造的成本后，再接既定的有限研究预算与节余再投资。可比较的同质量效率差额必须有证据；未知费用、质量缺失或重复执行证据不创造信用。避免支出的反事实估计也不是供应商返还的现金。

再往后才是持续多代实验，以及依据真实数据估计探索的边际价值。当前不制定固定的“策略最优分数”，也不宣称已证明效率驱动的持续递归增长。

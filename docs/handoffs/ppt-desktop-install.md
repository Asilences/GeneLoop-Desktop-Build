## 桌面接线

从仓库根目录运行以下命令。输出目录应是本次安装包构建的全新暂存目录。

```sh
node apps/desktop/scripts/stage-ppt-desktop.mjs <暂存目录>
```

入口校验仓库内的 ZIP 和解压后资源摘要，并保留 `local-ppt-deck.mjs` 与 `ppt-deck/` 的相对位置。构建时读取返回的 `ppt_master.root` 和 `sha256` 作核对。应用运行时从安装资源根目录定位 `ppt-deck/scenarios/ppt_master/third_party/ppt-master`。仓库中的 ZIP 只用于构建暂存。

1. **构建时暂存。** 先安装仓库锁定的 Node 构建依赖。由安装包构建调用完整资源入口，把输出目录放进 Electron 的安装资源，例如 `extraResources`。Python 脚本、模板和素材应放在 ASAR 外，由主进程按安装目录解析。运行时不使用构建机绝对路径或外部 `GENELOOP_PPT_MASTER_ROOT`。暂存目录包含原生引擎入口、PPT 制作资源及原 MIT 和第三方许可证。
2. **原生稿。** 从暂存目录加载 `local-ppt-deck.mjs`，通过 `createLocalPptDeckTools(host)` 注册 `build_ppt` 和 `patch_ppt`。宿主提供 `projectRoot`、`imagePath`、`theme`、`authorize` 和 `render`，可指定 `fontFamily`。保留项目 ID、页 ID、`revision` 和取消信号。同稿局部修订传当前 `expected_revision`。
3. **SVG 和已有 PPTX。** 从安装资源定位内置 `scripts/`。SVG 新稿沿用 `svg_quality_checker.py` 和 `svg_to_pptx.py`。复杂改稿用 `pptx_to_svg.py --roundtrip` 导入、在项目副本修改目标页、用 `svg_to_pptx.py --roundtrip` 导出。原生 `patch_ppt` 处理已有 JSON 源稿。若桌面已有直接 OOXML 改字路线，继续复用并纳入同一验收。桌面宿主提供按需 Python 和所需依赖，以参数数组调用批准的脚本。输入原件只读，输出写任务目录。
4. **预览和交付。** 宿主用各平台实际可用的 Office 渲染器和字体生成 PDF、逐页 PNG，按当前稿件版本登记 PPTX 与预览。`render` 接收 `{root, revision, slide_count, signal}`。现有服务器渲染器和编辑入口含 Linux 沙箱路径，桌面以本机工作区与渲染器实现该接口。保留目标页和文件摘要，让同会话改稿只更新当前交付。桌面包装层按需执行，本阶段无需增加常驻 PPT 服务。模型请求沿桌面现有服务器路由。

## Windows 和 Mac 验收

两端都从实际安装包启动。使用干净用户目录，清除外部 PPT Master 路径，不借用源码目录或历史安装。用同一组输入材料，记录安装包版本、操作系统和架构、渲染器版本、字体以及内置资源摘要。

| 用例 | 两端必须检查 |
| --- | --- |
| 原生生成和同会话改页 | 生成三页含中英文、图件、原生图表与备注的可编辑 PPTX。只改第二页，验证修改可见，非目标页及备注保留。关闭并重新打开应用后仍能找到当前稿件和预览。 |
| SVG 和复杂模板 | 用相同的封面、双系列图表、表格模板生成三页。检查图表和表格仍为原生对象，数据与素材一致，中文可读，无溢出、裁切或空白页。 |
| 已有 PPTX 改页 | 用带图表、表格和备注的稿件改封面。原件哈希不变；图表数据、表格和非目标页内容保留。对同一平台的改前改后渲染比较非目标页。 |
| 预览和下载 | 上述各项都有可打开的当前 PPTX、对应页数的 PDF 和逐页 PNG。导出失败或版本已变时，旧预览不作为当前成品发布。 |

先用固定输入验证上述路径，再从安装后的主聊天做一次生成和同会话改页，核对本机确实执行了对应工具并返回成品。跨平台比较内容、编辑性和版式，像素比较在同一平台、同一渲染环境内进行。每端回传通过或失败、产物、关键日志与差异。缺少真实安装包或只通过开发目录时，仍记待验。
